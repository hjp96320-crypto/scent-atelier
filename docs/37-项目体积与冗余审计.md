# 项目体积与冗余审计

日期：2026-11-09。只做只读检查并保存报告，未删除资源、未修改应用行为。
以下使用十进制 MB / GB；统计基线为生成本报告前，新增审计文件会使目录略有增加。

## 结论

项目共 **3.778 GB、40,335 个文件**。网页目录约 **925 MB**；其他约 **2.853 GB（75.5%）** 是研究数据、分析环境及开发资料。项目文件夹大小不等于网页首屏下载量。

| 部分 | 体积 | 判断 |
| --- | ---: | --- |
| research | 2,344.95 MB | 原始下载、来源证据、研究输入和实验产物；网页运行不依赖此目录 |
| prototype | 925.00 MB | 当前网页及本地资源，含少量测试和审核页 |
| .venv-analysis | 497.58 MB | 重新计算聚类需要的 Python 环境，打开网页不需要 |
| design-preview | 9.45 MB | 历史设计方案和截图 |
| docs / scripts / artifacts 等 | 约 1.36 MB | 文档、维护脚本和验证产物，占比较小 |

`启动设计预览.ps1` 已把 HTTP 根目录设为 `prototype`，并未把整份研究目录发给浏览器。

## 1. 已确认的下载冗余：优先级最高

`research/catalog-full/` 中同时存在：

- `images.zip`：875,465,236 字节（875.47 MB）。
- 53 个 `part-*.bin` 和 32 个 `small-*.bin`：共 **909,019,668 字节（909.02 MB）**。

逐个读取分片，对比文件名偏移对应的 ZIP 字节：**85/85 完全一致**。ZIP 内 26,422 个成员的 CRC 校验通过。因此，在保留完整 ZIP 的前提下，分片已是重复的下载中间产物，是最明确的清理候选。

仅清理这些分片，项目可从约 **3.78 GB 降至 2.87 GB**，减少约 24%。此项不改变网页资源和图鉴条目。

ZIP 本身也是下载归档，网页使用的是解压后的图片。若另有可靠备份，可移出日常工作目录；不能把“网页不依赖”理解成“无须保留原始来源”。

## 2. 图片：确有重复，但绝大部分是产品内容

- 最终合并后的图鉴：**26,335 条、26,335 个图片路径**；本地图片均存在。
- `prototype` 内图片总计 **899.74 MB**，占网页目录约 **97.3%**。
- 按文件大小分组后计算 SHA-256：发现 **143 组字节完全相同的图片，219 份额外副本**；统一引用可节省 **12.04 MB**。
- 另有 **84 张、3.02 MB** 图片没有被最终 `perfumes[].image` 使用，其中部分仍被历史审核页或覆盖前的数据行引用。
- 上述两类存在重叠，合并收益为 **12.44 MB**，不能简单相加。

图片去重应改为多个档案引用同一文件，保留所有香水 ID、版本、图片来源和核查信息；不能因瓶图相同就合并 EDT / EDP 档案。84 张候选图也应检查审核页和构建脚本后再清理。

若要明显缩小约 925 MB 的网页目录，主要方向是图片编码优化。当前许多数据库图片已是约 500px 的 JPEG，不能未经抽样质量验证就承诺压缩比例。

## 3. 研究和环境：应与运行包分开

| 候选 | 体积 | 处理建议与影响 |
| --- | ---: | --- |
| `.venv-analysis` | 497.58 MB | 不进入运行包；移除后需按锁定依赖重建，才能重新计算聚类 |
| 其中 `__pycache__` | 120.03 MB | 可再生缓存，和环境整体体积重叠，不重复计算收益 |
| 项目自身 `__pycache__` | 0.23 MB | 可再生，收益很小 |
| `research/catalog-pyramids-discovery` | 227.28 MB | 候选发现及 dry-run 产物；运行包排除，证据与可再生成中间产物分别保留 |
| `research/catalog-visualization` | 178.76 MB | 包含旧版比较实验及当前生成所需输入，不能整目录当垃圾删 |
| `research/catalog-enrichment` | 83.91 MB | 来源抓取与补充核查材料；运行包排除 |
| `research/catalog-100` | 47.02 MB | 早期采集和审核材料；归档，不按过时阶段直接删除证据 |
| `design-preview` | 9.45 MB | 旧设计预览，可归档 |

另确认 `research/catalog-visualization/input.json` 与 `v2/input.json` 的 SHA-256 相同，重复一份 **18.25 MB**。但两套脚本可能按各自相对路径读取，统一路径或归档实验后才能去重。两份 `prepared.json` 大小接近但内容不同，未计为重复。

建议保留“工作项目”和单独的“运行包”边界。运行包只携带网页、所需数据/图片、图库许可证及启动文件；研究证据和环境留在工作项目。仅分离运行包即可避免携带约 2.85 GB 开发资料，但这不等于电脑磁盘已释放相同空间。

## 4. 代码与加载：主要问题是全量加载，不是 JS 文件太多

静态追踪 `app.js` 的本地模块依赖后，**45 个生产模块均可达**；未发现可直接整文件移除的孤立生产 JS。27 个测试文件合计仅 **83.75 KB**，应保留在开发项目、从运行包排除。

### 全库进入每个页面

`app.js:15` 静态导入 `data.js`，后者加载全量数据并完成合并、补充、中文展示转换；`app.js:43` 随即为所有档案建立搜索文本。

- 可达 JS / 数据源文件合计约 **13.77 MB**，其中 `catalog-full-rows.js` 为 **11.33 MB**。
- 原始英文介绍列序列化约 **5.08 MB**；保留列结构但将内容抽离，可使该数据文件从约 11.33 MB 降为 6.33 MB。当前中文界面主要使用中文说明与香调解读，原始介绍可作为按需详情/证据加载，不宜无备份丢弃。
- 本机服务实查为 Python SimpleHTTP，响应没有 `Content-Encoding`。可达模块逐文件 gzip 实测合计约 **5.05 MB**，这是离线压缩估算，不是当前网络实测或已实现效果，也不包含图片、CSS、运行时 JSON 和图库。

优化顺序：今日/调香先加载自身必需内容；图鉴进入时再加载搜索索引；详情资料按需读取；生成轻量展示数据，内部来源留在独立证据文件；提供支持压缩的静态服务或构建产物。

### 星图和地图资源被一起加载

`catalog-atlas.mjs:13–17` 的 `Promise.all` 一次性加载星图、世界底图、行政区、品牌位置、局部分组与 deck.gl。

其中行政区 **3.49 MB**、世界底图 **1.59 MB**。只打开星图也加载这些地图资源，可按视图拆分加载；这是减少等待和内存占用，不减少离线包必须保留的地图体积。

### 模块版本参数不一致

只追踪生产模块，排除测试文件后，仍有 3 个模块存在不同导入 URL：

- `catalog-atlas-exploration.mjs`：`20261109-clusters` / `20261109-group-drilldown`。
- `blend-model.mjs`：有版本参数 / 无版本参数。
- `catalog-filter-groups.mjs`：有版本参数 / 无版本参数。

浏览器按完整 URL 区分模块，可造成重复模块实例。应统一版本策略；收益主要是避免重复解析/实例和维护歧义，节省的文件字节有限。

### 样式与旧逻辑候选

- 四份 CSS 合计 **129.43 KB**，存在基础 → 几何风 → UI polish 的叠加覆盖。应按组件整理，而不是直接删除整个旧样式文件。
- 静态扫描得到 **29 个未出现在生产 JS 和入口 HTML 中的 class 候选**，包括旧配方弹窗的 `.recipe-editor`、`.editor-row`、`.editor-add`，旧今日页的 `.day-aside`、`.journal-paper`，旧调整界面的 `.tip-compare`。动态拼接和其他 HTML 入口仍需复核；这不是浏览器 CSS coverage，也不证明所有候选都可删除。
- `catalog-atlas-exploration.mjs:26` 的 `clusterFocusRecords` 当前未被生产调用，仅测试仍在使用。它属于残留行为候选，可同步清理实现与对应旧测试，不能用“测试仍通过”证明实际 UI 仍采用该行为。
- 10 个 `catalog-review-*.html` 为历史图片审核入口，共约 24 KB，可移到研究/审核目录。

## 建议执行顺序

1. 清理已逐字节确认重复的 85 个下载分片：约 **909 MB**，收益最高且无需改应用。
2. 建立运行包白名单，排除环境、研究、测试和历史预览；保留工作目录中的来源证据及重建材料。
3. 按 SHA-256 合并图片路径、检查未使用图片，预计净省约 **12.44 MB**；验证全部 26,335 个 ID、版本及图片仍可用。
4. 拆分页面/图形数据加载、统一模块版本参数；这是体感速度优化重点。
5. 最后整理旧 CSS、未调用函数和审核页；体积收益有限，但降低后续维护成本。

本轮仅审计，没有执行上述清理，也未改变用户香柜、作品或日记。
