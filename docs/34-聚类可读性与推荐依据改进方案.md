# 聚类可读性与推荐依据改进方案

日期：2026-11-09。状态：已按用户确认实施，结果见 [[35-群组内部视图与推荐清单实施]]；三个局部试点中两个通过门槛，绿茶组暂不开放。以下保留实施前的问题诊断及原方案。

## 一、现状核查

当前不是单纯的缩放问题，而是把不同含义叠在了一张图上：

1. 群组由纯香调特征经 10 维 UMAP、HDBSCAN、两次种子一致性筛选生成。
2. 二维位置来自另一套模型：75% 香调特征与 25% 香型标签的 t-SNE。
3. 圆点颜色按首个香型标签显示，不是按群组显示。
4. 选中群组后，其他档案仍能被鼠标拾取并显示卡片，视觉上很难识别其身份。

本轮直接核对发布数据：

| 项目 | 结果 |
| --- | --- |
| 全库档案 | 26,335 |
| 稳定群组 | 33 组，共 8,501 条归属 |
| 未形成稳定归属 | 17,834 条，仍可正常浏览 |
| “梨 · 茉莉”组 | 190 条；全部列有梨类线索，113 条列有茉莉类线索 |
| 该组首个香型 | 花香 147、琥珀 14、木质 14、柑橘 5、馥奇 3、西普 5、皮革 2 |
| 该组每点在二维图最近 15 点中的同组成员均值 | 约 4.76，即约 31.7%；这里只衡量当前屏幕邻域，不是气味准确率 |
| 截图中的 Rose Somptueuse | ID `hf-full-11856`，群组为 `-1`，不属于“梨 · 茉莉” |

所以该图目前更适合称为“香气关系分布”，不宜让用户以为一个名称下面就是一块明确分区。标签里的两种香调也是群组概括，不保证每款同时包含两者。

证据：`research/catalog-visualization/cluster-manifold.py`、`joint-tsne.py`、`consensus.py`、`prototype/assets/atlas/atlas-data.json`、`prototype/catalog-atlas-renderer.mjs`。

方法边界：UMAP 官方说明指出，UMAP 与 t-SNE 都不能完整保留密度，也可能把一个群体在投影中撕裂。因此不能仅凭二维图上分开的斑块认定存在二级类别。[官方说明](https://umap-learn.readthedocs.io/en/latest/clustering.html)

## 二、推荐的图形方案：全库概览 → 群组内部 → 具体香水

### 全库概览

- 标题使用“香气分布”，保留连续全局坐标及密度层。
- 默认颜色表达群组归属，选择后以清晰统一的选中色显示本组；按香型着色移到可选图形选项中。
- 数量多的群组通过标签与分级显示呈现，不同时塞入 33 种难以区分的颜色。颜色仅辅助识别，名称、描边和数量共同表达归属。
- 未形成稳定归属的档案用中性底色，另有可访问的列表入口，不能称为“错误数据”。
- 群组名称改为更容易理解的气味概括，并显示主要线索及覆盖情况，例如“梨香花果方向”，展开后说明“梨类 190/190；茉莉类 113/190”。这些比例来自资料，不代表香料浓度。

### 点选群组

- 明确进入“本组香水”状态，右侧显示完整成员、数量与本组气味线索。
- 本组成员突出，外围背景极淡保留上下文；默认禁止背景点响应悬停和点击。需要探索外围时，用户显式点“返回全图”。
- 本组成员列表与图中可交互成员使用同一 ID 集合；截图中的雅芳款不能再在该组产生悬停卡片。
- 第一阶段仍使用现有坐标，明确“主要分布”与完整成员的区别，不再把缩放当作聚类修复。

### 群组内部视图

- 第二阶段增加独立局部视图，仅显示本组成员，并根据本组的完整香调特征重新展开位置；醒目标注“仅比较本组香水”。
- 全局坐标保持冻结。局部视图是另一张图，不暗中重排全图；退出时恢复进入前的全局视角。
- 使用一致的特征口径试算局部分组和投影，同时验证原始香调关系、局部可读性与跨种子稳定性。不能仅为让点聚拢而调整成规则岛屿。
- 若存在稳定且有可解释香调差异的子群，再显示子群名称、代表香水和数量；没有可靠子群则直接显示成员，不强行补成二级分类。
- 远离主体的成员保留，并用“边缘成员”解释资料上的差异；不从数量或列表中删除。二维离得远本身不能作为移除其归属的依据。

交互路径：

`全库香气分布 → 梨香花果方向 → 本组内部视图 → 有依据的子群（可选）→ 香水详情`

不建议再次使用按首香型打包的固定岛屿，也不建议只调大热力图模糊半径。两者都会改善轮廓，却掩盖当前分组与位置不一致的问题。

## 三、推荐独立维护：资料清单 + 发布清单 + 展示记录

目前实现只是 `reviewedProfile` 档案池、香型评分、日期轮换，未使用独立的情境核查清单。现有 100 个已核查版本可作为首批资料来源，但不自动认定它们适用于所有情境。

### 1. 推荐资料清单

每行对应一个精确香水版本，建议独立维护在 `research/recommendations/catalog.json`，审核后生成运行时文件。

| 字段 | 内容 |
| --- | --- |
| 香水身份 | 稳定 ID、品牌、名称、EDT/EDP 等具体版本、匹配图片 |
| 气味事实 | 已核查香调、官方或可靠资料链接、证据摘录、核查日期 |
| 场景判断 | 适合的天气与场景、气味依据、限制与反例；明确属于编辑建议 |
| 推荐解释 | 面向用户的一句话，能对应到该版本的实际资料 |
| 状态 | 待核查、可推荐、暂停；资料冲突时暂停，不自动补造依据 |
| 维护信息 | 内容版本、最近修改、修改原因、下次复核日期 |

“含有佛手柑”不足以直接推出“适合炎热天气”；需要结合主体和后段气味判断。留香、扩散、强度无可靠依据时不添加精确数值。

### 2. 本期发布清单

- 建议按周维护一期，日常按本地日期轮换；日期变化不代表资料每天重新核查。
- 每期记录：生效时间、候选版本 ID、适用情境、入选原因、新增/修改/暂停项、清单版本。
- 首批整理现有 100 款，覆盖当前 4 种天气 × 3 种场景；每种情境争取具备多个可靠候选，不为了数量凑入不合适款。
- 发布前校验 ID、浓度、图片、证据与推荐状态；核查失败的条目不进入本期。
- 默认先过情境适配门槛，再结合近期重复、品牌多样性与当天轮换排序。候选足够时避免连续重复；不足时如实说明，不假装有无限选择。
- 个人香柜仍优先；香柜款未进入经过情境核查的清单时，可作为“香柜探索”，不能继承“本期精选”的依据标识。
- “热门”需要单独的热度证据；没有可靠榜单来源时，入口文案改为“从本期精选找灵感”。

### 3. 本地展示记录与用户入口

- 展示记录保存日期、情境、推荐版本 ID、匹配原因、清单版本、是否手动切换，用于避免重复和解释“为什么今天推荐它”。不新增云端上传。
- 推荐卡保留简洁外观，增加两个轻入口：“为什么推荐”和“本期清单”。
- “为什么推荐”展示该版本气味事实、当前情境的编辑判断和需留意之处；不把编辑判断伪装成品牌官方结论。
- “本期清单”显示本期候选、适用情境、最近更新日期和变更摘要；详细来源仍在内部资料层维护，不堆回主卡片。
- “每日轮换”与“资料更新于某日”分开显示，避免用户误以为每日自动抓取了新资料。

## 四、实施顺序与验收

1. **先修正群组身份表达**：禁用群组外拾取、统一选中色、列表和图中可交互 ID 一致、改进标签解释。验收样例固定为“梨 · 茉莉”、晚香玉及稀疏记录。
2. **建立独立推荐清单**：先处理现有 100 个具体版本，增加入选理由、清单版本及用户查看入口。验收每次推荐都能追溯到清单条目；排除暂停、证据冲突和版本不一致条目。
3. **试算局部群组视图**：先选三个不同分布的真实群组，比较局部投影与子群稳定性，提交真实数据预览。通过后再扩展其他组；不提前承诺固定子群数或完全分离的外形。

共同验收：返回恢复视角；筛选人数一致；全部成员可访问；手机点选与桌面悬停不混淆组内外；每日轮换不重复冒充资料更新；推荐更换后仍能解释其入选依据。

本方案不新增后端、公开部署或应用封装，不改变现有香柜、日记与配方。
